# Пункт 4: комментарии к блокам изменённого кода

`workflow_hw.json` публикует по одному inline-комментарию к каждому текстовому
блоку diff (`@@ … @@`). Поддерживаются автоматическое ревью при открытии PR,
команды `/make_ai_review` и `/make_other_ai_review`.

## Настройка в n8n

1. Импортируйте обновлённый `workflow_hw.json` в ваш проект n8n.
2. Проверьте credentials:
   - GitHub Trigger и ноды публикации **GitHub Robot1** / **GitHub Robot**
     используют существующий **GitHub account 42**;
   - **Get PR Metadata**, **Get PR Files**, **Check PR Snapshot** используют
     существующий **Bearer Auth account 27**;
   - Chat Model использует ваш существующий credential OpenAI-совместимого API.
3. Для чтения достаточно `Pull requests: Read`, для публикации нужно
   `Pull requests: Read and write`. Триггерам также нужны права на webhooks.
4. Проверьте таблицу `ai_reviewed_prs` во всех четырёх Data Table нодах.
   Схема таблицы не изменилась; настройка описана в
   [DATA_TABLE_SETUP.md](DATA_TABLE_SETUP.md).
5. Убедитесь, что к каждому агенту подключены его Chat Model и общий
   **Hunk Review Output Parser**, а **Require Specific Output Format** включён.
6. Сохраните и активируйте workflow. Для ручной проверки комментариев
   запускайте тестирование именно из **PR Comment Trigger**.

Код обработки встроен в JSON: импортировать отдельные JS-файлы в n8n не нужно.

## Маршрут выполнения

После проверки пары `pr_id` + `model` обе ветки используют общий путь:

```text
Prepare Review Context
    → Get PR Metadata
    → Get PR Files
    → Split PR Into Hunks
    → Has Text Hunks [true]
    → Select Review Model
        ├─ true  → Code Review Agent1 + OpenAI Chat Model1
        └─ false → Code Review Agent  + OpenAI Chat Model
    → Build Inline Review
    → Check PR Snapshot
    → Verify PR Snapshot
    → Select Review Publisher
        ├─ true  → GitHub Robot1 → Store Main AI Review → Add Label to PR1
        └─ false → GitHub Robot  → Store Other AI Review → Add Label to PR
```

`review_branch` выбирает агента и публикацию: `main` для основной модели,
`other` для второй. Модель получает все разобранные блоки одним запросом,
а её ответ должен содержать отдельный комментарий к каждому блоку.

## Получение изменений и координаты строк

**Get PR Metadata** запрашивает `GET /repos/{owner}/{repo}/pulls/{number}`.
Из ответа сохраняются `head.sha` и `base.sha` — снимок анализируемого PR.
SHA файла из `/files` не используется в качестве SHA коммита.

**Get PR Files** запрашивает `/pulls/{number}/files` с `per_page=100` и
пагинацией `page = $pageCount + 1`. Загрузка заканчивается на странице
с менее чем 100 файлами. Далее количество файлов проверяется по
`changed_files` из метаданных, чтобы не опубликовать частичное ревью из-за
неполной пагинации. GitHub возвращает не более 3000 файлов через этот endpoint.

**Split PR Into Hunks** разбирает `patch` каждого файла по заголовкам `@@`.
Для каждого блока создаются:

- `block_id`: путь файла + порядковый номер блока;
- `path`: точный `filename` из GitHub API, включая новый путь при переименовании;
- `patch`: текст этого блока с контекстом;
- `anchors`: допустимые изменённые строки для комментария.

Номера считаются отдельно для старого и нового файла:

| Строка patch | Счётчики | Привязка |
| --- | --- | --- |
| `+` | Новый номер увеличивается | `RIGHT`, номер новой строки |
| `-` | Старый номер увеличивается | `LEFT`, номер старой строки |
| Пробел, контекст | Оба номера увеличиваются | Не предлагается модели как anchor |
| `\ No newline at end of file` | Не изменяются | Нет |

Поддерживаются блоки с нулевыми диапазонами, добавленные и удалённые файлы,
несколько блоков в одном файле, CRLF и отсутствие перевода строки в конце файла.
Счётчики проверяются по заголовку блока и полям `additions` / `deletions`.
Обрезанный patch завершает выполнение ошибкой до публикации и записи в таблицу.

## Ответ модели и публикация

Structured Output Parser требует такой ответ:

```json
{
  "comments": [
    {
      "block_id": "src/example.py:hunk:1",
      "anchor_id": "R12",
      "body": "При count == 0 возникнет ZeroDivisionError. Добавьте проверку перед делением."
    }
  ]
}
```

`anchor_id` выбирается из `anchors` соответствующего блока. Модель не задаёт
собственные `path`, `line` и `side`. Если явных проблем нет, она должна кратко
сообщить об этом, а не выдумывать замечание для заполнения комментария.

**Build Inline Review** проверяет, что:

- каждому блоку соответствует ровно один комментарий;
- нет неизвестных или повторных `block_id`;
- выбранный anchor действительно относится к изменённой строке этого блока;
- текст непустой и не превышает 6000 символов.

Координаты комментария берутся из разобранного patch. Все комментарии
публикуются одним `POST /repos/{owner}/{repo}/pulls/{number}/reviews`:

```json
{
  "commit_id": "head.sha анализируемого PR",
  "event": "COMMENT",
  "body": "AI-ревью моделью … Проверено блоков изменений: …",
  "comments": [
    {
      "path": "src/example.py",
      "line": 12,
      "side": "RIGHT",
      "body": "Замечание к блоку изменений"
    }
  ]
}
```

Вместо устаревающего `position` используются `line` и `side`.
Ноды **GitHub Robot1** и **GitHub Robot** теперь имеют тип **HTTP Request**
и используют **Predefined Credential Type → GitHub API**, сохраняя существующие
credentials публикации.

Перед POST ноды **Check PR Snapshot** и **Verify PR Snapshot** повторно
проверяют `head.sha` и `base.sha`. Если PR изменился, публикация отменяется
и запись в Data Table не создаётся. Команду можно отправить повторно.

## Файлы без текстового patch

Бинарные файлы, чистые переименования и другие файлы без доступного `patch`
перечисляются в общем тексте review как непроверенные. Для них нет вычисляемых
координат, поэтому inline-комментарии не создаются.

Если текстовых блоков нет вообще, **Has Text Hunks [false]** переходит сразу
к **Build Inline Review**. Модель не вызывается, публикуется только сообщение
об отсутствии текстовых блоков и список пропущенных файлов.

## Дедупликация PR + модель

Проверки **Only Unreviewed PRs** и **Only Unreviewed Other PRs** выполняются
до любых запросов файлов и вызовов модели. Совпадать должны оба поля —
`pr_id` и `model`. После публикации всех inline-комментариев создаётся одна
строка с URL review. Вызов другой модели разрешён, повтор той же — пропускается.

При смене модели обновите Chat Model и поле `model` в **Prepare Main PR**
или **Prepare Other PR**. Триггеры и их различные webhook ID сохранены.

## Проверка и материалы для сдачи

1. Подготовьте PR с двумя изменёнными файлами и несколькими раздельными
   `@@`-блоками хотя бы в одном файле. Для теста второй модели используйте PR,
   у которого ещё нет строки с этой моделью в таблице.
2. Отправьте `/make_other_ai_review` новым комментарием в **Conversation**.
3. В **Executions** откройте:
   - **Split PR Into Hunks**: должны быть отдельные `blocks` с anchors;
   - ответ агента: по одному элементу `comments` на блок;
   - **Build Inline Review**: массив с `path`, `line`, `side`, `body`;
   - **GitHub Robot**: успешный ответ с `html_url`;
   - **Store Other AI Review**: одна запись после публикации review.
4. В **Files changed** убедитесь, что комментарии находятся у изменённых строк
   разных блоков, включая `LEFT` для блока только с удалениями.
5. Вызовите вторую команду повторно: она должна закончиться на проверке таблицы.
   Основная модель для того же PR должна быть доступна, если ещё не запускалась.
6. Приложите ссылку на PR, скриншоты inline-комментариев, Executions и таблицы,
   а также экспорт сценария из вашего n8n.

Локальные проверки встроенного кода и маршрутов с подменёнными ответами API:

```bash
node --test workflow_hw.test.cjs
```

Они не обращаются к GitHub и моделям. Доставку webhook, подключение parser в
вашей версии n8n и публикацию комментариев нужно подтвердить реальным запуском.
