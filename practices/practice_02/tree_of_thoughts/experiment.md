# Tree of Thoughts

- Решение, для которого нужны альтернативы:
Как структурировать нагрузочные проверки в `tests_load.md` с фокусом на REL-1/OUT-1 под нагрузкой, воспроизводимость окружения и отказные сценарии API-1/422.
- Критерии выбора:
Минимальность правок, соответствие CASE (REL-1, OUT-1, API-1), воспроизводимость (окружение, метрики, Evidence), понятность для CI.

## Запрос
Сгенерируй 3 альтернативных варианта структуры `tests_load.md`, учитывая критерии. Каждый вариант должен включать таблицу сценариев и разделы Environment и Metrics & Evidence. Не вводи произвольные пороги задержки; pass/fail — по правилам CASE. Выбери лучший и предложи итоговый текст правок.

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A | Табличная структура с тремя сценариями: Stable baseline, Error storm (REL-1+OUT-1), Validation under load (API-1/422) | Меньше гибкости для будущих сценариев | Высокая: минимальные правки, ясные pass/fail |

| C | Сценарии пошагово (Given/When/Then) + сводная таблица метрик | Длиннее документ | Средняя: понятнее тестировщикам, но тяжелее поддерживать |

## Выбор

- Выбранная альтернатива:
А — табличная структура из трёх ключевых сценариев.
- Почему:
Минимальные правки, прямая привязка к CASE (REL-1/OUT-1/API-1), удобна для CI и отчётов.
- Как проверим:
Сопоставим критерии pass/fail с CASE.md; убедимся, что Evidence-артефакты перечислены и метрики воспроизводимы.
