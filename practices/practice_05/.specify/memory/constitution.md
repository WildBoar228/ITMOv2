# Конституция проекта «Quiz‑карточки»

## Core Principles

### I. Схема данных — неизменна без парных тестов
Нельзя менять схему `project/data/decks.json` без синхронного обновления проверки
в `validateDeck()` (project/app.js) и тестов (`tests/test_decks.py`). Схема строгая:
вопросов ≥ 1; ровно 4 варианта; `correct` — индекс 0–3; `explain` опционален и,
если присутствует, является строкой (пустая строка эквивалентна отсутствию).
Рационал: стабильность данных и воспроизводимость автопроверок.

### II. Фиксированный таймер и отсутствие персиста
`TIME_PER_QUESTION` фиксирован и равен 15 секундам, шаг таймера — 200 мс.
Прогресс и счёт не сохраняются между сессиями, используется только память процесса.
Импорт/экспорт JSON — единственный механизм персиста. Рационал: простота,
сопоставимость результатов и соответствие тестам.

### III. Границы UI и стилей
Стили правятся только в `project/style.css`. Инлайн‑стили в JS допустимы лишь
для ширины таймера (`#timer-bar.width`). Радиокнопки правильного ответа в
редакторе должны иметь один `name` на вопрос. Рационал: предсказуемые правки,
читаемость и контроль регрессий стилями.

### IV. TDD и обязательные проверки
Любая фича/фикс, затрагивающие `project/app.js`, идут по TDD: сначала падающий
тест, затем минимальная реализация, затем полный прогон:
`python3 -m json.tool project/data/decks.json`, `node --check project/app.js`,
`pytest -q`. Хук `.opencode/plugins/quiz-check.js` может запускать проверку
автоматически при правках в `project/`. Рационал: предотвращение регрессий.

### V. Интеграция с MCP и импорт/экспорт
Для агентных сценариев используем MCP‑сервер `quiz` (`mcp/quiz_server.py`):
`list_decks`, `get_question` (без утечки `correct`), `check_answer` (возвращает
результат и `explain`), `validate_deck` (проверка JSON). Веб‑приложение остаётся
локальным (без сетевых зависимостей), персист — только экспорт/импорт JSON.
Рационал: безопасная автоматизация и чистые контракты доступа к данным.

## Дополнительные ограничения

- Технологии UI: локальная страница без сборки, vanilla JS/DOM, файлы в `project/`.
- Стиль: классы карточек/кнопок (`.deck-card`, `.opt-btn`, `.timer`, `.card-actions`,
  `.icon-btn`) поддерживаются и модифицируются только через CSS.
- Удаление игр — только через нативный `confirm()`; отмена = без изменений.
- Никакого `localStorage`/cookie/бэкенда для счёта и состояния.

## Workflow разработки и качество

- Перед мержем проверяются: схема `decks.json`, константа таймера в `app.js`,
  границы стилей (отсутствие лишних инлайн‑стилей), валидность импорт/экспорт.
- Для фич, меняющих поведение в `project/app.js`, обязательны стат‑тесты на
  исходники по образцу `tests/test_feature_b.py` или юнит‑прогоны `validateDeck`
  через Node, как в `tests/test_decks.py`.
- Команды для локальной проверки:
  - `python3 -m http.server 8000` (страница: `/project/`)
  - `python3 -m json.tool project/data/decks.json`
  - `node --check project/app.js`
  - `pytest -q`

## Governance

- Эта конституция имеет приоритет над прочими практиками в проекте `dz/`.
- Любая правка схемы или принципов требует MR/PR с:
  1) формулировкой изменения; 2) обновлением тестов и `validateDeck()`;
  3) миграционными заметками для существующих колод.
- Версионирование конституции: SemVer.
  - MAJOR — несовместимые изменения принципов/процедур.
  - MINOR — добавление новых принципов/секций или существенное расширение.
  - PATCH — правки формулировок/уточнения без изменения смысла.
- Комплаенс‑проверка: ревьюер проверяет соответствие всем принципам и чек‑листу
  из раздела «Workflow разработки и качество» в каждом PR.
